# WebSocket 并发连接压测报告

## 结论

以下第一部分保留 Nginx 调优前的历史基线；最新结论见文末“第二轮：Nginx 调优与 HTTP/活跃链路压测”。测试对象均为测试环境公网入口 `https://117.72.159.185/tmk-test`，每条连接均经过登录鉴权、创建独立 Session、HTTPS/WSS Nginx 反向代理和服务端所有权校验。

- 观测到的最大同时稳定连接数：**417**。该轮请求 500 条连接，83 条握手失败，因此不能作为可承诺容量。
- 满足至少 99% 建连成功率的边界：请求 390 条，成功并稳定保持 **388** 条，成功率 99.49%。
- 零握手失败、零保持期断连的安全容量：**375** 条。
- 当前配置建议运行上限：**300** 条同时连接，为突发 HTTP 请求、Prometheus 抓取和连接分布不均保留约 20% 余量。

当前首先触达的瓶颈是 Nginx `worker_connections 768`。错误日志明确记录 `768 worker_connections are not enough while connecting to upstream`。Go 服务没有崩溃，成功建立的连接在 60 秒保持阶段均未发生非预期断连。

## 测试环境

| 项目 | 配置 |
|---|---:|
| CPU | 2 vCPU |
| 内存 | 1975 MB |
| Swap | 0 |
| Nginx | `worker_processes auto`、`worker_connections 768` |
| 测试服务文件句柄上限 | 524288 |
| ASR 配置 | Bailian，本轮未启动 ASR 管线 |
| 压测入口 | 公网 HTTPS/WSS，经 Nginx 代理 |

Nginx 代理一条 WebSocket 会同时占用客户端连接和到 Go 服务的 upstream 连接，因此入口连接槽消耗高于直接连接应用端口。测试服务器还同时运行 MySQL、Prometheus、Java 服务及其他业务进程。

## 测试方法

每轮按以下步骤执行：

1. 使用真实账号登录并获取 Access Token。
2. 为每条连接创建独立 Session，验证数据库写入与会话所有权。
3. 在 10 至 20 秒内平滑建立目标数量的 WSS 连接。
4. 每 15 秒发送 WebSocket Ping，并持续读取服务端消息。
5. 全部连接保持 60 秒，统计保持期断连。
6. 正常关闭连接并批量删除本轮 Session。
7. 同时采集应用 RSS、文件句柄、整机可用内存和 `tmk_websocket_connections`。

压测工具位于 `TMK-Glance/cmd/ws-loadtest`，密码只能通过 `TMK_LOADTEST_PASSWORD` 环境变量传入，不写入命令参数或报告。

## 资源峰值

| 指标 | 峰值或最低值 |
|---|---:|
| `tmk_websocket_connections` | 417 |
| Go 服务 RSS | 33.5 MB |
| Go 服务文件句柄 | 428 |
| 整机最低可用内存 | 113.8 MB |

Go 服务从空闲时约 13 MB RSS 增长到约 33.5 MB，空闲 WebSocket 的应用侧内存增长不是本轮首要瓶颈。整机可用内存较低，主要原因是同机 MySQL、Java 服务和其他系统进程，后续进行持续音频与 ASR 压测前需要增加 Swap 或释放同机内存。

## 边界解释

“最大连接数”需要区分三种口径：

- **观测峰值 417**：证明服务曾同时保持这些连接，但该轮整体建连失败率为 16.6%。
- **99% 边界 388**：目标 390 时满足常用的至少 99% 建连成功标准，但已经出现 Nginx 容量错误。
- **零失败容量 375**：本轮所有连接均成功建立并稳定保持，是当前配置最适合作为简历和容量说明的数字。

因此对外应表述为：“当前 2 核 2 GB 单机测试环境，经 Nginx 代理可稳定保持 375 条空闲 WebSocket 长连接；观测峰值 417，入口瓶颈为 Nginx worker connections。”不应表述为支持 417 条业务活跃同传连接。

## 限制

本报告测量的是经过鉴权、Session 和 Nginx 的长连接容量，不是持续音频处理容量。测试环境当前连接真实 Bailian ASR，若同时启动数百条 ASR 会产生外部费用并触发供应商并发配额，因此本轮没有发送 `start` 或 PCM 音频。

业务活跃容量还需要在 mock ASR 隔离环境中补测：持续发送 16 kHz PCM、字幕下行、翻译调度、音频丢弃率、CPU 和 GC。生产可承载的活跃同传数还会受到 Bailian ASR 和翻译服务配额约束。

## 优化建议

1. 将 Nginx `worker_connections` 提高到 4096，同时确认 worker 数量和 `worker_rlimit_nofile`。
2. 为测试服务器增加 1 至 2 GB Swap，或将占用约 400 MB 的 Java 服务和测试环境分离。
3. Nginx 调优后重新执行 500、750、1000 阶梯测试，验证瓶颈是否转移到内存、网络或 Go 调度。
4. 建立 mock ASR 隔离压测实例，补充持续 PCM 的活跃连接容量报告。
5. 将安全运行上限配置为 300，并在 `tmk_websocket_connections` 超过 300 时告警。

## 第二轮：Nginx 调优与 HTTP/活跃链路压测（2026-08-17）

本轮测试服务版本为 `bcf9af3`。Nginx 已调整为 `worker_rlimit_nofile 65535`、`worker_connections 4096`，配置备份位于服务器 `/etc/nginx/nginx.conf.pre-tmk-ws-loadtest-20260817`，并已通过配置检查后热加载。生产服务版本未修改。

### HTTP 接口

测试接口为需鉴权的 `GET /api/v1/languages`，每轮持续 15 秒，结果是该代表性读接口在当前单机环境下的吞吐，不代表所有 API 的统一上限。

| 并发 | 请求数 | QPS | P95 | P99 | 错误率 |
|---:|---:|---:|---:|---:|---:|
| 10 | 1,395 | 92.99 | 321 ms | 840 ms | 0 |
| 50 | 7,183 | 478.85 | 330 ms | 624 ms | 0 |
| 100 | 6,740 | 449.31 | 722 ms | 2,081 ms | 0.0148%（1 次超时） |

并发 50 时吞吐最高且无错误；并发 100 已出现排队和长尾，当前可将约 50 并发作为该接口的稳定压测参考点。

第二轮在 2,000 条空闲连接下仍然全部稳定，说明首轮 417 条的限制确实来自 Nginx 768 个连接槽，而不是 Go 应用本身。当前仍未测试 2,000 条以上的边界；考虑到机器只有 2 vCPU、约 2 GB 内存且与 MySQL/Prometheus 同机，建议暂将测试环境安全运行值设为 1,500 条，并在扩容内存或拆分数据库后继续阶梯测试。

### 活跃 PCM、ASR 与翻译链路

为避免真实云服务费用和供应商并发配额影响，测试环境临时启用内置 `loadtest` ASR 和 `mock` 翻译，测试结束后已恢复原有环境变量并重启测试服务。50 条连接保持 30 秒，按 100 ms 发送 3,200 字节 PCM 帧。

| 指标 | 结果 |
|---|---:|
| 客户端发送音频帧 | 19,709 |
| 客户端写失败 | 0 |
| 服务端接收帧 | 19,709 |
| 服务端丢弃帧 | 0 |
| 音频帧丢弃率 | 0% |
| ASR 流完成数 | 50（均为正常关闭时的 cancelled） |
| ASR 错误数 | 0 |
| ASR 平均流持续时间 | 39.47 s |
| 翻译 partial 请求 | 405，平均 19.5 ms，失败 0 |
| 翻译 final 请求 | 406，平均 14.6 ms，失败 0 |

ASR 指标记录的是一次实时流从 `start` 到结束的流持续时间，并非单帧识别延迟；本轮连接正常关闭，所以 ASR 被标记为 `cancelled`，不应计入错误率。按“error / (success + error)”计算，ASR 和翻译失败率均为 0%。真实 Bailian ASR/翻译的网络耗时、配额错误和供应商失败率需要在低并发、受控预算下另行基线，不能用 mock 结果替代。

### 采集与复现

压测工具为 `TMK-Glance/cmd/http-loadtest` 和 `TMK-Glance/cmd/ws-loadtest`。应用 Prometheus 指标 `tmk_asr_request_duration_seconds`、`tmk_translation_duration_seconds`、`tmk_websocket_audio_chunks_total` 分别提供 ASR/翻译耗时直方图和音频 accepted/dropped 计数；报告中的丢帧率按测试前后计数差计算：`dropped / (accepted + dropped)`。密码只通过 `TMK_LOADTEST_PASSWORD` 环境变量传递，不写入命令行或报告。
