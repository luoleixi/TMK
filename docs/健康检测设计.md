# 健康检测设计

## 目标

健康检测区分进程存活、应用就绪和外部能力状态，避免部署脚本仅凭 HTTP 200 就认定新版本可用。

## 探针

| 接口 | HTTP 语义 | 使用者 |
| --- | --- | --- |
| `GET /api/health/live` | 进程能够处理 HTTP 时始终返回 200 | systemd、容器平台的存活检测 |
| `GET /api/health/ready` | 核心初始化完成返回 200，否则返回 503 | 部署、负载均衡和流量切换 |
| `GET /api/health` | 始终返回 200 的兼容概览 | 管理后台和旧监控 |

应用只有在数据库连接及迁移、管理员引导检查、对象存储初始化和评测任务管理器启动全部成功后才进入 ready。应用关闭时先撤销 ready，再停止工作线程和数据库连接。

## 状态模型

- `starting`：核心初始化尚未完成，不应接收业务流量。
- `ok`：应用已就绪，已注册的外部能力检查均正常；未配置的可选能力不影响此状态。
- `degraded`：应用已就绪，但至少一个已注册的外部能力不可用。基础管理和数据功能仍可访问，具体能力应按业务降级策略处理。
- `service_states.* = unknown`：该能力没有注册运行时检查，不等同于故障。
- `service_states.* = unavailable`：检查已执行但失败，或检查器自身发生异常。

为兼容现有调用方，响应继续提供布尔型 `services`；新增的 `service_states` 承担三态表达。响应不包含数据库地址、密钥、错误堆栈等敏感配置。

## 部署与回滚

测试和生产部署脚本在原子切换版本并重启 systemd 服务后，最多等待 30 秒访问本机 `/api/health/ready`。只有收到 2xx 才完成部署；否则输出有限的 systemd 状态和近期日志，并切回上一版本。GitHub Actions 随后通过 Nginx 的外部地址再次检查 ready，覆盖反向代理和路径配置。

生产发布仍只能人工触发。生产服务通过就绪检查后，客户端发布任务才允许继续。

## 后续扩展

拆分服务后，各服务分别实现 live/ready；网关的 ready 只检查处理请求所必需的核心依赖。异步工作节点不对外提供流量，其就绪条件应改为数据库、队列和对象存储可用。外部 ASR、翻译服务的检查应设置短超时，并通过缓存或后台采样避免每次探针请求都触发远程调用。
