# 可观测性设计

## 组成

TMK-Glance 采用“JSON 日志 + Prometheus 指标 + 存活/就绪探针”的三件套：

- 标准输出日志由 systemd/journald 收集，统一为 JSON，包含服务名、环境和请求 ID。
- `/metrics` 只监听应用本机端口；Nginx 对 `/tmk-test/metrics` 和 `/tmk-production/metrics` 返回 404，避免公网暴露内部指标。
- `/api/health/live` 只表示进程存活，`/api/health/ready` 表示数据库和对象存储等核心依赖可以接流量。

## 指标

HTTP 指标按方法、规范化路由和状态码统计，避免将用户路径和查询参数作为高基数标签。业务指标包括：

- HTTP 请求数、延迟、正在处理请求数
- WebSocket 当前连接数、连接持续时间、音频帧接收/丢弃数
- ASR 流请求数、成功/失败/取消次数和请求持续时间，按实时会话与离线评测区分
- HTTP 和 WebSocket 翻译请求数、成功/错误/降级次数、延迟
- 评测任务和评测条目成功/失败次数、任务执行耗时、排队等待耗时，以及租约回收、自动重试和死信状态转换
- MySQL 连接池、等待次数、评测队列 queued/running
- 对象存储已用字节和文件系统剩余空间

不记录音频内容、原文、译文、Authorization、Cookie 或 API 密钥。

## 运行时采样

应用启动后立即采样，之后每 15 秒刷新一次数据库、评测队列和对象存储状态。采样失败会将服务置为 not ready；依赖恢复后自动恢复 ready。外部 ASR、翻译服务不在 HTTP 探针中同步调用，后续应增加有超时和缓存的后台探测。

## 告警

`deploy/prometheus/tmk-alerts.yml` 提供基础规则：指标抓取失败、HTTP 5xx 比例过高、评测队列持续积压和对象存储剩余空间不足。阈值应按测试、生产实际流量调整，通知渠道由服务器上的 Alertmanager 配置。

## 部署

`deploy/prometheus/tmk-prometheus.yml` 是 Prometheus 的抓取模板，测试端口为 `18080`，生产端口为 `8080`。Prometheus 应部署在服务器本机或受限管理网络中；不应通过公网反向代理暴露指标端点。JSON 日志由 journald 保留并按环境分离，生产环境应配置轮转和远端归档。

服务器已安装 Prometheus 时，可使用 `/usr/local/sbin/tmk-configure-observability` 校验并安装抓取与告警规则。日志等级通过 `LOG_LEVEL=debug|info|warn|error` 配置，测试和生产默认使用 `info`。

## 结构化日志

所有标准输出均由 `slog` JSON Handler 输出，并由 systemd/journald 收集。HTTP 日志包含 `request_id`、规范化路由、状态码和耗时；WebSocket 日志包含 `session_id`、连接持续时间和 ASR 结果；翻译日志包含模式、语言方向、结果和耗时；异步任务日志包含 `job_id`、`dataset_id`、`worker_id`、尝试次数、结果和执行耗时。

日志不写入音频、原文、译文、Authorization、Cookie 或 API 密钥。成功的高频 ASR/翻译细节使用 debug 级别，失败和降级使用 warn，任务结束使用 info/warn，便于控制生产日志量。

## 查询建议

- 可用性：`up`、`/api/health/ready`、HTTP 5xx 比例
- 性能：HTTP 和翻译直方图的 p50/p95/p99
- 实时体验：WebSocket 连接数、音频丢弃率、翻译 fallback 比例
- ASR：`sum(rate(tmk_asr_requests_total{outcome="error"}[10m])) / sum(rate(tmk_asr_requests_total{outcome=~"success|error"}[10m]))`、ASR p95 持续时间
- 翻译：`histogram_quantile(0.95, sum by (le) (rate(tmk_translation_duration_seconds[10m])))`
- 评测运营：队列长度、任务排队等待、任务执行耗时、单条目耗时、失败率
- 容量：对象存储字节数、剩余磁盘和 MySQL 连接池等待
