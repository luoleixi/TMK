# 身份与权限设计

## 目标与边界

身份系统同时服务 TMK 桌面客户端和后续 Web 管理后台。服务端是唯一可信的权限执行点，前端隐藏按钮不能代替服务端授权检查。

当前角色：

| 角色 | 权限 |
|---|---|
| `user` | 登录、改密、实时翻译、访问和管理自己的会话 |
| `admin` | 具有普通用户权限，并能创建、查询、禁用用户、调整角色、重置密码、认领旧会话 |

当前采用 RBAC 两角色模型。评测后台增加后，可扩展为 `operator`、`annotator`、`reviewer`，不建议把权限判断散落成邮箱白名单。

## 认证设计

- 密码使用 bcrypt 保存，数据库不保存明文或可逆密文。
- 密码长度限制为 12 至 72 字节，72 字节是 bcrypt 的输入上限。
- Access Token 默认有效 15 分钟；Refresh Token 默认有效 30 天。
- Token 是 32 字节加密安全随机数，响应中以 64 位十六进制字符串返回。
- 数据库只保存 Token 的 SHA-256 摘要，数据库泄露后不能直接使用摘要登录。
- Refresh Token 每次使用都会轮换，旧 Refresh Token 立即失效，不能重放。
- 退出会撤销当前 Access Token 和 Refresh Token。
- 禁用用户、修改角色、修改或重置密码会撤销该用户现有令牌。
- 同一邮箱和 IP 在 15 分钟内连续失败 5 次后临时限制登录。生产环境还应在 Nginx 或网关增加分布式限流。
- 桌面端令牌仅保存在进程内存，退出应用后需要重新登录，不写入明文设置文件。

桌面端在 Access Token 临近过期或收到 401 时，会串行执行一次 Refresh Token 轮换并重试原请求。WebSocket 在 HTTP Upgrade 请求的 `Authorization` 头中携带 Access Token。

## 数据库变更

服务启动时通过幂等迁移自动创建或更新结构，MySQL 与 SQLite 都受支持。

### `users`

保存账号主体：`id`、唯一邮箱、显示名称、bcrypt 密码摘要、`role`、`status`、首次登录强制改密标志、创建/更新时间和最后登录时间。

### `auth_tokens`

保存可撤销令牌：令牌 ID、用户 ID、类型、SHA-256 摘要、过期时间、创建时间和撤销时间。通过外键关联用户，删除用户时令牌级联删除。

### `audit_logs`

保存安全操作：操作者、动作、资源、IP、User-Agent、结果、JSON 详情和时间。登录成功/失败、退出、创建和修改用户、重置密码、认领旧会话均会记录。

### `sessions.user_id`

新增可空的会话所有者，并建立 `(user_id, created_at)` 索引。所有会话详情、历史查询、摘要、删除、停止和 WebSocket 连接都会检查所有权。访问他人资源统一返回 404，避免泄露资源是否存在。

升级前的会话被保留，`user_id` 为 `NULL`，不会自动暴露给任何新用户。管理员确认归属后调用旧会话认领接口一次性分配。

## 首次部署

在测试与生产环境各自的 `/etc/tmk/<environment>/tmk.env` 中设置：

```dotenv
AUTH_BOOTSTRAP_ADMIN_EMAIL=admin@example.com
AUTH_BOOTSTRAP_ADMIN_PASSWORD=replace-with-a-random-password
AUTH_ACCESS_TOKEN_TTL_MINUTES=15
AUTH_REFRESH_TOKEN_TTL_DAYS=30
CORS_ALLOWED_ORIGINS=https://admin.example.com
```

服务器初始化脚本会安装两个辅助命令。首次升级前可以执行：

```bash
sudo ./scripts/bootstrap-server.sh
sudo tmk-configure-auth test admin@example.com
sudo systemctl restart tmk-glance@test.service
```

命令会生成随机初始密码并写入权限为 `0640` 的环境文件，只在终端显示一次。生产环境将 `test` 替换为 `production`。

Bootstrap 管理员只在 `users` 表为空时创建，避免环境变量长期拥有重置管理员的能力。首次登录必须修改密码。确认用户已创建后，应从环境文件删除两个 `AUTH_BOOTSTRAP_ADMIN_*` 值并重启服务。

```bash
sudo tmk-clear-bootstrap-auth test
sudo systemctl restart tmk-glance@test.service
```

如果数据库中没有任何用户且未提供 Bootstrap 凭据，服务端会拒绝启动，部署健康检查会失败并回滚，避免发布出一个无人能够管理的环境。

测试和生产必须使用不同管理员密码、数据库和环境文件。

## API

公开接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/auth/login` | 邮箱密码登录 |
| `POST` | `/api/v1/auth/refresh` | 轮换刷新令牌 |
| `GET` | `/api/health` | 健康检查，不返回敏感配置 |

需要 Access Token：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/auth/me` | 当前用户 |
| `POST` | `/api/v1/auth/logout` | 撤销当前令牌 |
| `POST` | `/api/v1/auth/change-password` | 修改自己的密码并撤销全部令牌 |

除上述登录/刷新接口外，原有 `/api/v1` 业务接口都必须携带 `Authorization: Bearer <access_token>`，且首次密码未修改时不能调用。

管理员接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/admin/users` | 分页查询用户 |
| `POST` | `/api/v1/admin/users` | 创建用户，用户首次登录必须改密 |
| `PATCH` | `/api/v1/admin/users/{id}` | 修改显示名、角色、状态和强制改密标志 |
| `POST` | `/api/v1/admin/users/{id}/reset-password` | 设置临时密码并撤销全部令牌 |
| `POST` | `/api/v1/admin/legacy-sessions/claim` | 将所有无归属旧会话认领给指定用户 |

系统拒绝禁用或降级最后一个有效管理员。

## 上线顺序

1. 先备份 MySQL 数据库并在测试环境部署服务端，让自动迁移完成。
2. 创建 Bootstrap 管理员、登录并修改初始密码。
3. 通过管理员接口创建普通用户。
4. 确认旧会话归属后执行一次认领；不要在多人共用历史时盲目全部认领。
5. 发布带登录功能的新桌面客户端。旧客户端没有认证头，服务端升级后会收到 401，因此服务端与客户端需要按同一发布窗口切换。
6. 验证登录、刷新、WebSocket、用户隔离、禁用用户和退出撤销。
7. 删除 Bootstrap 密码环境变量，再部署生产环境。

## 后续增强

- 管理后台上线时采用同一认证 API，但 Refresh Token 应改用 `Secure`、`HttpOnly`、`SameSite` Cookie，并配套 CSRF 防护，不应暴露给浏览器 JavaScript。
- 多实例部署时，把登录限流迁到 Redis 或 API 网关。
- 审计日志应增加管理员分页查询和只追加归档策略。
- 对管理员和高风险操作增加 TOTP/WebAuthn 多因素认证。
- 接入企业身份源时优先使用 OIDC，不自行扩展第三方登录协议。
